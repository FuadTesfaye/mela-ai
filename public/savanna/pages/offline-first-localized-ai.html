When the internet says no

Raise your hand if you have ever wanted to use AI, but the internet said no.

Too slow. Too expensive. No signal at all.

03 / 18

4 reasons AI must work offline

Connectivity: slow, costly or missing internet outside big cities.

Privacy: health and student data never has to leave the device.

Cost: every cloud AI request costs money and mobile data.

Speed: no trip to a far-away server; instant answers.

04 / 18

Offline-first = a generator for your app

The power cuts. The generator starts. The lights stay on.

Offline: everything important still works. Core features work. For AI this means the model runs locally.

Online: sync, updates, bigger models. Connection adds bonus features and extras.

05 / 18

Where should the AI run?

A — Cloud: a huge remote server. Most powerful, but needs internet, charges per use, and data leaves the device.

B — Local: on the user’s device. Works offline, private and free per use, but models are smaller and limited by the device.

C — Hybrid: local first, cloud when online. Best of both, with more to design and test.

Our pick for most projects: C, Hybrid, with local as the default.

06 / 18

Small models, big possibilities

Model size is measured in parameters: the numbers inside a model.

Big cloud models: hundreds of billions. Laptop-size models: about 8 billion. Phone-size models: about 1–3 billion.

Text and chat: Gemma, Llama, Phi, Qwen. Speech: Whisper for speech-to-text. Translation: NLLB, about 200 languages. Images: small vision models.

Always check each model’s licence before building a product on it.

07 / 18

Quantization = compressing a photo

Same picture. Much smaller file. Original full-precision numbers are the 100% baseline.

Quantize to 4-bit: look for Q4 or 4-bit labels; up to about 8× smaller.

Pick the smallest model that does the job. Distil: a big teacher trains a small student. Focus on one job: focused beats general.

08 / 18

Pick your stage

Phone: LiteRT, Core ML, ONNX Runtime, MediaPipe. Great fit for field apps.

Laptop: Ollama, llama.cpp, LM Studio. Great fit for staff tools and demos.

Browser: WebGPU, Transformers.js, WebLLM. Nothing to install.

Local server: one machine on local Wi-Fi can serve a whole school or clinic.

Optional live demo: AI running with Wi-Fi off.

09 / 18

Myth vs fact

Myth: AI always needs the internet. Fact: small models run fully offline on laptops and phones.

Myth: local AI is useless. Fact: for one focused task, a small model is often good enough.

Myth: fine-tuning needs millions of examples. Fact: with LoRA, hundreds to a few thousand good examples can help.

10 / 18

Integrating an AI model in 5 steps

1. Define the task.

2. Pick a model.

3. Test with real data.

4. Shrink and package.

5. One interface.

The secret is step 5: your app asks “summarise this” and never cares which model answers. Like a phone charging socket: plug in any charger.

11 / 18

One socket, swappable engines

Your app connects to an AI layer or router.

Online and allowed? Use cloud. Otherwise, use local.

The local model is always available; the cloud model is optional when online.

Sync queue: save on the device first, upload when the connection returns.

12 / 18

Does AI speak our language?

Most AI learned mostly from English. Amharic, Afaan Oromo and Tigrinya have far less training data.

Illustrative tokenization: “hello” can be one piece; “ሰላም” can be split into more pieces. Ge’ez script may require more tokens, making processing slower, less accurate or costlier.

More pieces mean more work for the model.

Localization is not just translation. “Buying apples at Walmart for $3” in perfect Amharic is still strange. Use local names, places, money and examples.

13 / 18

3 ways to make AI local

Easy — Go multilingual: start from models trained on many languages and test several.

Medium — Open-book exam (RAG): the model looks up your documents, such as a curriculum or health guides, before answering. This can work offline.

Advanced — Fine-tune (LoRA): teach a small model with local examples using a cheap add-on instead of a full retrain.

Golden rule: test with native speakers. No score replaces a real human.

14 / 18

Reality check

Device limits: test on the cheapest phone your users own, not yours.

Quality: keep a test set of real local examples; native speakers review.

Model updates: download big models on Wi-Fi only and version every model.

Licences and safety: check licences and tell users AI can be wrong.

What would you build first?

Offline tutor: answers students’ questions in their own language, with no internet.

Clinic assistant: speak notes in the local language and turn them into an organised record.

Farmer helper: a photo of a sick plant leads to a likely disease and advice.

Voice access: speech-to-text for people who prefer speaking.

Shout out your idea!

18 / 18

4 things to remember

1. Design for no internet; connection is a bonus.

2. Small, quantized models run on phones, laptops and local servers.

3. One interface: swap local and cloud models freely.

4. Localize: multilingual models, local knowledge and native speakers.

Downloadable file

Insert a file hosted at a public https:// URL as a clickable download link. The icon and label are auto-detected from the file extension. Use the tool in the editor toolbar to generate it.

Auto-detected types: image (.jpg, .jpeg, .png, .gif, .webp, .svg, .bmp, .ico), video (.mp4, .mov, .webm, .avi, .mkv, .m4v), pdf, notebook (.ipynb), python (.py), js (.js, .jsx, .mjs, .cjs), c (.c, .h), text (.txt, .md, .csv, .log). Unrecognized extensions render with a generic file icon.

Rive Animations

The recommended way to embed a Rive animation is the Library Files tool () in the editor toolbar: pick a .riv asset, choose its artboard and data bindings, and insert it. This produces a library-anchored ::asset ID ... :: tag whose overrides are independent on each page — double-click an inserted asset to reopen the configurator. The raw ::rive data: form below is a low-level escape hatch.

Per-page overrides. The same library asset can render a different artboard, state machine or data bindings on each page. The overrides are configured in the Library Files tool and stored on the tag as a Base64 data: payload (::asset 42 data:<base64-json> ::) — you do not construct this by hand; double-click an inserted asset to reopen the configurator. The src, dimensions, brand and version still resolve from the library file, so the asset stays anchored. 

::rive data: <base64-encoded-JSON> ::

JSON shape:

{
  "src": "https://example.com/animation.riv",
  "width": 1920,
  "height": 540,
  "stateMachine": "State Machine 1",
  "artboard": "MasterBanner",
  "viewModelName": "mbViewModel",
  "viewModelInstanceName": "Instance",
  "bindings": {
    "bannerTitle": "Introduction to the Learning Content",
    "courseSelect": "artboard:SAMPLE_ARTBOARD"
  }
}

Fields:

  • src — URL to the hosted Rive file (.riv) — required
  • width, height — canvas size in pixels (defaults: 400×225)
  • stateMachine — name of the state machine to play
  • artboard — name of the artboard to render (uses default if omitted)
  • viewModelName, viewModelInstanceName — data binding View Model and instance names
  • bindings — object of { propertyName: value } pairs. Type (string, number, boolean, color, enum) is auto-detected. Use "artboard:<name>" as the value to bind an artboard property (e.g., to swap branded variants).

Dynamic values. Binding values may embed {{key}} placeholders, replaced per learner at render time (e.g. "Hello {{learner.first_name}}"). Available keys: learner.first_name, learner.last_name, learner.full_name, learner.email, course, brand, page_name, locale.

Worked example. The JSON {"src":"https://example.com/animation.riv","stateMachine":"State Machine 1"} becomes:

GitHub Content

GitHub content embeds pull a file from a repository's default branch at render time and display it inline. Use the GitHub insert tool in the editor toolbar to fill in the fields and validate the paths — you do not need to construct this by hand. 

::github-content data: <base64-encoded-JSON> ::

JSON shape:

{
  "org": "<org>",
  "repo": "<repo>",
  "path": "<path/to/file.md>",
  "files": ["<path/to/file1.py>", "<path/to/file2.py>"]
}

Fields:

  • org — GitHub organization or user — required
  • repo — repository name — required
  • path — path to the main content file, relative to the repository root — required
  • files — array of supporting file paths, rendered as download links above the main content. Each path is relative to the repository root (same format as path).

Markdown files (.md, .markdown) are rendered inline; other UTF-8 text files are shown in a code block, while non-UTF-8/binary files show a warning instead. Fetched content is cached for 1 hour.

Chidi InlineChat

Chidi embeds use a single data: attribute holding a Base64-encoded JSON config. Use the Chidi insert tool () in the editor toolbar to generate it; double-click an existing tag to edit its config in place — you do not need to construct this by hand. 

::chidi data: <base64-encoded-JSON> ::

JSON shape:

{
  "activityType": "tutor",
  "apiUrl": "https://example.com",
  "cssUrl": "https://example.com/inline/llm-tutor-inline.css",
  "greeting": "Hello! I'm here to help.",
  "jsUrl": "https://example.com/inline/llm-tutor-inline.js",
  "starters": ["I'm ready", "Check my code"],
  "systemPrompt": "You are a helpful tutor..."
}

Fields:

  • jsUrl, cssUrl, apiUrl — URLs for the InlineChat assets and API — required
  • greeting — initial greeting displayed to the student — required
  • starters — array of suggested starter prompts (optional)
  • systemPrompt — system prompt for the AI tutor — required
  • activityType — one of tutor, reflection, guide, content_clarity
